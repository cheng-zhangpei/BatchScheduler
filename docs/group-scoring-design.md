## 1. 我们已经决定做什么

第一版保留两项组评价：**通信评价、可选的资源整合评价**。

先根据通信关系组织少量可行放置方案，再评价这些方案的通信效果和资源分布，结合已有 Pod 基础分选出最终计划。

```text
Pod Filter：每个 Pod 有哪些可行节点
    ↓
Pod Score：每个候选节点的基础分
    ↓
通信规划：链路候选 → reduce → 少量不同的组放置方案
    ↓
组评价：通信评价＋可选的资源整合评价
    ↓
结合 Pod 基础分统一汇总
    ↓
选出一套最终 Pod → Node 计划
    ↓
Assume → Bind
```

这是一套方案选择框架。单个 Pod 的节点分数是输入，不直接各取最高分作为最终计划。

## 2. 每套候选方案包含什么

概念上的候选列表叫 `[]CandidatePlan`。这是讨论中的名字，本次没有增加 Go 类型。

每套方案要能回答：

| 内容 | 回答的问题 |
| --- | --- |
| Pod → Node 映射 | 本轮每个成员最终放到哪里 |
| Pod 基础评价 | 这些位置在前面的 Pod Score 中表现如何 |
| 通信分数和明细 | 哪些关系达到期望、哪些发生降级 |
| 资源整合分数和明细 | 开启优化时，方案留下的资源空间如何 |

方案需要覆盖本轮参与放置的成员，包括没有声明通信关系的成员。

多套方案要保留不同放置方式，不能只是同一种分布换几个节点名字。第一版先留下少量可行备选继续流程；具体数量、搜索预算和多样性算法以后再定。

最终只选一套方案，转换成 Executor 接收的 `Pod → Node` 计划。其余方案的试放不能成为实际资源占用。

## 3. 通信这一条线

### 3.1 输入

- 每个 Pod 的候选节点、基础分和资源需求。
- Group 内显式声明的通信关系或通信子组。
- 每条关系的期望靠近等级、放置权重、冲突妥协顺序。
- 相关成员的集中偏好。
- 同组当前已绑定成员的位置，以及可用的跨 Unit 上下文。

通信声明如何进入 CR、端点怎样命名、拓扑等级使用哪些标签，还没有确定。

### 3.2 做什么

1. 对每条关系生成候选位置：同节点可以是一个共同节点，跨节点则记录两端分别落在哪个节点。
2. reduce 合并链路候选，形成组方案，检查共享成员的位置是否一致、累计资源是否足够。
3. 冲突时按关系的妥协顺序放宽靠近等级，继续形成可行方案。
4. 对方案的通信效果评分，保留实际靠近等级和降级原因。

放置权重表达关系对通信评价的重要程度，允许相同；妥协顺序用于决定冲突时先放松谁。它们都不是 Pod 优先级。

通信域是一组承载 Node 及其拓扑范围。资源充足时，倾向寻找能同时承载多条关系的域，减少关系之间的争抢。

### 3.3 输出

多套可行组方案，以及各自的通信分数和明细。通信偏好降级后仍可正常调度，不因此进入 Fail/Retry。

详细流程和例子见[通信语义方案](communication-semantics.md)。

## 4. 资源整合这一条线

### 4.1 目标

让新增成员尽量利用合适的已有空间，留下更完整、后续更容易使用的资源。

这里集中的是集群资源占用。它与“同组成员集中在一起”可能给出不同选择。

例如：

```text
node1：已有任务，剩余 4 CPU
node2：已有任务，剩余 4 CPU
node3：完整空闲，剩余 8 CPU

本组 A、B 各需 4 CPU
```

| 方案 | 放置结果 | 留下的空闲资源 |
| --- | --- | --- |
| A、B 都去 node3 | 本组集中在一个节点 | node1、node2 各剩 4 CPU |
| A 去 node1、B 去 node2 | 填补已有空间 | node3 保留完整 8 CPU |

只看 CPU，第二套方案保留了能容纳一个 8 CPU Pod 的完整节点。第一套方案可能更符合组内通信偏好。这正是最终需要权衡的两项评价。

### 4.2 用户可以选择是否开启

提供一个是否允许内置资源整合优化的开关。字段名称、默认值和具体配置位置留待实现时确定。

- 关闭：不额外加入这项组级资源整合评价，按用户其他声明的偏好及 Pod 基础评价选择。
- 开启：对候选方案增加资源整合评价，与通信评价及 Pod 基础评价一起参与选择。

这个开关不关闭 Pod Filter 的资源检查，也不关闭已有 Pod Score 资源插件。它控制的是新增的组方案资源整合评价。

开启不代表碎片永远优先，更不授权违反用户硬约束。它只授权我们在允许的方案之间进行资源与通信的权衡。

### 4.3 怎样评价

在资源副本上模拟整套方案放完后的节点余量，再评价是否填补了合适的空隙、保留了完整空间。

实际要联合考虑 CPU、内存等资源。不同资源的剩余形状会影响后续可用性，单纯数用了几个节点还不够。

当前只确定目标和开关，碎片指标与评分公式尚未确定。我们也不知道未来任务一定需要什么，因此资源分数只能表达选定指标下的偏好，不能保证未来吞吐最优。

## 5. 最后怎样汇总

每套方案分别保留：Pod 基础评价、通信评价、开启时的资源整合评价。

最终比较必须先满足这两层前提：

1. Pod 的硬约束成立，节点来自其可行列表。
2. 整套方案的累计资源需求放得下。

然后才比较可行方案的各项分数。通信偏好的降级顺序在候选规划阶段处理，最终分数不能把不可行方案选回来。

如果一套方案通信更好、资源分布也更好，且其他条件相同，应当优先选择它。如果通信和资源各有优劣，就按用户允许的偏好进行权衡，不称其中一套为无条件的“最优”。

分数范围、Pod 分数怎样聚合成方案评价、各项怎样归一化及加权、同分怎样决定，都留到汇总实现时逐项确定。本次定下的是评价组成与处理顺序，没有定下数值公式。

解释结果时保留各项分数和降级明细，让我们能看到最终为什么选择这套方案。

## 6. 第一版明确不扩展的部分

- 不加入独立的同步优化。缺少执行阶段信息时，无法仅凭位置判断谁造成同步等待。
- 不自行推导副本与容错方案。副本数量、替代关系和恢复由工作负载或 Operator 决定；将来调度器落实明确声明的放置约束。
- 不对已运行成员自动迁移。本次只规划当前待调度成员，已有成员的位置作为参照。
- 不实现后台继续搜索。先用少量备选推进流程，后台补充方案、停止信号和搜索预算以后再讨论。
- 不强制合并冻结的 Unit。组语义通过跨 Unit 上下文延续，实际执行仍有本轮成员边界。
- 不承诺真实通信速度最优。拓扑靠近是第一版采用的近似，仍需硬件和负载测试。
