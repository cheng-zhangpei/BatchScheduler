## 1. 我们已经决定做什么

第一版保留两项组评价：**通信评价、可选的资源整合评价**。

先根据通信关系组织少量可行放置方案，再评价这些方案的通信效果和资源分布，结合已有 Pod 基础分选出最终计划。

从搜索角度，通信语义主导部分方案的扩展和保留，集中语义在保留的完整候选上评分。搜索取舍与最终评分分开：生成时要保留不同放法，评分阶段才能比较通信与资源的取舍。当前按成员数量保留不同布局只是初步办法，不保证保留所有其他语义偏好的方案，也不保证全局最优。

```text
Pod Filter：每个 Pod 有哪些可行节点
    ↓
Pod Score：每个候选节点的基础分
    ↓
通信规划：链路候选 → reduce → 少量不同的组放置方案
    ↓
组评价：通信评价＋可选的资源整合评价
    ↓
结合 Pod 基础分统一汇总
    ↓
选出一套最终 Pod → Node 计划
    ↓
Assume → Bind
```

这是一套方案选择框架。单个 Pod 的节点分数是输入，不直接各取最高分作为最终计划。

## 2. 每套候选方案包含什么

候选列表叫 `[]CandidatePlan`，类型位于 [planner/types.go](../src/scheduler/planner/types.go)。

`Placements` 保存 Pod 到节点的映射，`Scores` 分开保存三项评价，`Communication` 保存逐条规则及实际等级，`Notes` 解释方案和通信降级。`Scores.Consolidation=nil` 表示没有资源整合评分结果，不等同于零分。

每套方案要能回答：

| 内容 | 回答的问题 |
| --- | --- |
| Pod → Node 映射 | 本轮每个成员最终放到哪里 |
| Pod 基础评价 | 这些位置在前面的 Pod Score 中表现如何 |
| 通信分数和明细 | 哪些关系达到期望、哪些发生降级 |
| 资源整合分数和明细 | 开启优化时，方案留下的资源空间如何 |

方案需要覆盖本轮参与放置的成员，包括没有声明通信关系的成员。

多套方案要保留不同放置方式，不能只是同一种分布换几个节点名字。第一版先留下少量可行备选继续流程；具体数量、搜索预算和多样性算法以后再定。

最终只选一套方案，转换成 Executor 接收的 `Pod → Node` 计划。其余方案的试放不能成为实际资源占用。

## 3. 通信这一条线

### 3.1 输入

- 每个 Pod 的候选节点、基础分和资源需求。
- Group 内显式声明的通信关系或通信子组。
- 每条关系的期望靠近等级、放置权重、冲突妥协顺序。
- 相关成员的集中偏好。
- 同组当前已绑定成员的位置，以及可用的跨 Unit 上下文。

2026-10-26 已增加 CR 声明及透传：`spec.placement.communication` 保存链路，`spec.placement.resourceConsolidation` 是资源整合开关。端点引用 Pod 的稳定 `scheduling.batchscheduler.io/member-id` 标签。字段说明见 [PodGroup 与成员关系](podgroup-view.md)，示例见 [podgroup-communication.yaml](../config/examples/podgroup-communication.yaml)。当前通信插件只处理两端都在本轮的关系，具体实现见[通信放置源码说明](communication-placement.md)。

### 3.2 做什么

1. 对每条关系生成候选位置：同节点可以是一个共同节点，跨节点则记录两端分别落在哪个节点。
2. reduce 合并链路候选，形成组方案，检查共享成员的位置是否一致、累计资源是否足够。
3. 冲突时按关系的妥协顺序放宽靠近等级，继续形成可行方案。
4. 对方案的通信效果评分，保留实际靠近等级和降级原因。

放置权重表达关系对通信评价的重要程度，允许相同；妥协顺序用于决定冲突时先放松谁。它们都不是 Pod 优先级。

通信域是一组承载 Node 及其拓扑范围。资源充足时，倾向寻找能同时承载多条关系的域，减少关系之间的争抢。

### 3.3 输出

多套可行组方案，以及各自的通信分数和明细。通信偏好降级后仍可正常调度，不因此进入 Fail/Retry。

详细流程和例子见[通信语义方案](communication-semantics.md)。

## 4. 资源整合这一条线

### 4.1 目标

让新增成员尽量利用合适的已有空间，留下更完整、后续更容易使用的资源。

这里集中的是集群资源占用。它与“同组成员集中在一起”可能给出不同选择。

例如：

```text
node1：已有任务，剩余 4 CPU
node2：已有任务，剩余 4 CPU
node3：完整空闲，剩余 8 CPU

本组 A、B 各需 4 CPU
```

| 方案 | 放置结果 | 留下的空闲资源 |
| --- | --- | --- |
| A、B 都去 node3 | 本组集中在一个节点 | node1、node2 各剩 4 CPU |
| A 去 node1、B 去 node2 | 填补已有空间 | node3 保留完整 8 CPU |

只看 CPU，第二套方案保留了能容纳一个 8 CPU Pod 的完整节点。第一套方案可能更符合组内通信偏好。这正是最终需要权衡的两项评价。

### 4.2 用户可以选择是否开启

开关为 `spec.placement.resourceConsolidation`，默认关闭；已经传到规划器，有集中插件且用户开启时才调用。具体集中插件仍未实现。

- 关闭：不额外加入这项组级资源整合评价，按用户其他声明的偏好及 Pod 基础评价选择。
- 开启：对候选方案增加资源整合评价，与通信评价及 Pod 基础评价一起参与选择。

这个开关不关闭 Pod Filter 的资源检查，也不关闭已有 Pod Score 资源插件。它控制的是新增的组方案资源整合评价。

开启不代表碎片永远优先，更不授权违反用户硬约束。它只授权我们在允许的方案之间进行资源与通信的权衡。

### 4.3 怎样评价

在资源副本上模拟整套方案放完后的节点余量，再评价是否填补了合适的空隙、保留了完整空间。

实际要联合考虑 CPU、内存等资源。不同资源的剩余形状会影响后续可用性，单纯数用了几个节点还不够。

当前只确定目标和开关，碎片指标与评分公式尚未确定。我们也不知道未来任务一定需要什么，因此资源分数只能表达选定指标下的偏好，不能保证未来吞吐最优。

## 5. 最后怎样汇总

每套方案分别保留：Pod 基础评价、通信评价、开启时的资源整合评价。

最终比较必须先满足这两层前提：

1. Pod 的硬约束成立，节点来自其可行列表。
2. 整套方案的累计资源需求放得下。

然后才比较可行方案的各项分数。通信偏好的降级顺序在候选规划阶段处理，最终分数不能把不可行方案选回来。

如果一套方案通信更好、资源分布也更好，且其他条件相同，应当优先选择它。如果通信和资源各有优劣，就按用户允许的偏好进行权衡，不称其中一套为无条件的“最优”。

通信插件目前先用 Pod 基础分求和、通信权重乘实际靠近分来做原始评价，说明见[通信放置源码](communication-placement.md)。首版选定沿用搜索排序，直接选择第一套完整候选，不重新计算总分。多语义分数范围、归一化与加权、同分怎样决定，仍待逐项确定。

解释结果时保留各项分数和降级明细，让我们能看到最终为什么选择这套方案。

## 6. 第一版明确不扩展的部分

- 不加入独立的同步优化。缺少执行阶段信息时，无法仅凭位置判断谁造成同步等待。
- 不自行推导副本与容错方案。副本数量、替代关系和恢复由工作负载或 Operator 决定；将来调度器落实明确声明的放置约束。
- 不对已运行成员自动迁移。本次只规划当前待调度成员，已有成员的位置作为参照。
- 不实现后台继续搜索。先用少量备选推进流程，后台补充方案、停止信号和搜索预算以后再讨论。
- 不强制合并冻结的 Unit。组语义通过跨 Unit 上下文延续，实际执行仍有本轮成员边界。
- 不承诺真实通信速度最优。拓扑靠近是第一版采用的近似，仍需硬件和负载测试。

## 7. 实现入口与当前状态

现有步骤入口是 [steps/plan.go](../src/scheduler/steps/plan.go) 的 `PlanGroup`，现在调用 [planner.Planner.Plan](../src/scheduler/planner/planner.go)。内部按链路放置、可选集中评分、自动优化预留位置、最终汇总的顺序组织，再返回最终计划。

[planner/plugins.go](../src/scheduler/planner/plugins.go) 先定义两个接口：`LinkPlacementPlugin.Place` 返回多套完整候选方案；`ConcentrationPlugin.Score` 只评价一套方案的资源分布，不修改放置位置。插件在启动前设置，不让 Buffer 协调这些内部环节。

默认已接 communication 插件，用户可通过 Executor.SetPlanner 替换。Planner 选出唯一计划后，Executor 报告 Planned 并批量 Assume；当前 Bind 尚未实现，会先调用 Recover/Forget 结清本轮暂占，再报告 Blocked。启用额外评分时，多语义比较仍返回 `ErrHandlerUnavailable`。自动优化暂时只有 TODO，没有新接口或后台线程。

Pod 基础分来自 [upstream/score.go](../src/scheduler/upstream/score.go)，基础评分说明见 [Pod Score](score.md)。这次不修改上游插件。

GroupScoreInput 已补充完整 Pod、NodeInfo、冻结的 Placement 声明和跨 Unit 上下文，通信插件从这份输入读取本轮数据。字段定义与源码一并保存在当前 checkpoint 中。

通信配置、冻结声明透传、本轮成员通信规划、首版计划选定和本地 Assume/Forget 已实现。跨 Unit 端点解析、资源整合评分、多语义汇总及真实 Bind 仍未完成，不能把本地资源闭环当作整个调度器已经跑通。

下一次先 review **steps.Assume → Cache.Assume → Recover/Forget** 的调用，再讨论 Bind。其他语义评分接口保留，不继续扩展评分公式。源码说明见[通信放置插件](communication-placement.md)。

先把一个问题讲清楚：前一步交给后一步什么，后一步返回什么。确认后再逐个实现链路候选、reduce、方案评价和汇总，不一次展开所有算法。

验证分两层：

- 现在能做：用构造的拓扑和资源数据验证约束、累计试放、降级、跨 Unit 位置参照，以及规划耗时和内存开销。

跨域关系减少是模型内可检查的结果，实际任务是否更快还需要实验。这是第一版设计的验证边界。
