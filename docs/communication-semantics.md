# 通信语义：从通信关系到组放置方案

更新日期：2026-10-26。

本文记录已经讨论的通信规划框架。当前已实现本轮成员的通信候选生成，并沿用搜索排序选定第一套完整计划，源码说明见[通信放置插件](communication-placement.md)。集中评分和多语义最终汇总仍待实现。

2026-10-27 已接入 Priority 排序：高值先处理，同值按名称。通信语义引导有限候选搜索，其他语义评价保留的完整方案；仍保留部分更远的候选供后续比较。

这次先确定输入、输出和处理顺序。搜索算法、评分公式和后台搜索方式以后再优化，不在这次设计中展开实现。

通信与资源整合两条线已经合并成[第一版组评分方案](group-scoring-design.md)。本文详细说明其中的通信部分。

## 1. 这一层到底要产出什么

输入：本轮各 Pod 的候选节点、基础分、资源需求，以及组内声明的通信关系。

输出：**少量可行的组放置方案，每套方案带通信分数和解释。**

例如，本轮要安排 A、B、C：

```text
候选方案一
  放置：A → node1，B → node1，C → node1
  通信分数：……
  通信关系的实际靠近等级：……
  哪些关系降级、为什么降级：……

候选方案二
  放置：A → node2，B → node2，C → node3
  通信分数：……
  通信关系的实际靠近等级：……
  哪些关系降级、为什么降级：……
```

每套方案必须明确每个 Pod 放在哪里。`list[list[node]]` 不足以说明 Pod 与 Node 的对应关系，因此概念上的输出是 `[]CandidatePlan`，每项包含 `Pod → Node` 映射。

这里的“组方案”会考虑整个 Group 的关系，实际可安排的成员仍是本轮 Unit 的成员。同组已绑定成员作为位置参照参与判断，不因为参与组规划就自动被迁移。

后续其他组语义继续评价同一批方案，最终汇总各项评价，选出一套计划，交给 Assume、Bind。通信分数、其他语义分数和原有 Pod 基础分要分别保留，便于汇总和解释。

## 2. 我们能优化什么

用户声明谁与谁通信；调度器决定这些成员落在哪些 Node 上。

第一版使用拓扑关系近似表达通信条件，例如同节点、同机架、同可用区。我们暂时假设更近的位置通常更值得优先尝试，但不把拓扑距离当成真实带宽或时延测量。

当前不接入逐链路遥测，不推断真实网络瓶颈，不调整通信算法。运行中的同步等待也暂时不单列为一种优化语义。

## 3. 通信声明需要表达什么

通信关系以 Group 为范围，可以通过显式成员关系或通信子组表达。本轮先按成员之间的关系来解释算法；子组以后也需要给规划器提供明确的成员范围。

| 信息 | 用来回答什么问题 |
| --- | --- |
| 通信端点 | 哪些成员之间有通信关系 |
| 期望靠近等级 | 希望同节点，还是同机架等 |
| 放置权重 | 满足这条关系，对方案的通信评价有多重要 |
| 冲突妥协顺序 | 多条关系无法同时满足时，先放松哪条 |
| 集中偏好 | 条件允许时，希望相关成员集中到什么程度 |

放置权重可以相同。发生冲突时，妥协顺序需要给出明确的先后；它针对通信关系，不是 Pod 优先级。相同妥协值的最终处理方式留给实现时确定，不能依赖遍历 map 的偶然顺序。

期望靠近等级和集中偏好也有区别：前者描述一条关系希望有多近，后者影响整套方案把相关成员集中在多大的范围内。

2026-10-26 已增加 `spec.placement.communication`，端点引用同组 Pod 的稳定 `scheduling.batchscheduler.io/member-id` 标签值。字段及示例见 [PodGroup 与成员关系](podgroup-view.md)。配置已传到 GroupScoreInput，本轮成员端点解析和可配置的拓扑标签映射已接入。

## 4. 已经确定的两条规则

### 规则一：优先满足靠近要求，冲突时允许降级

先尝试关系期望的靠近等级。无法形成可行方案时，允许逐步放宽，例如：

```text
同节点 → 同机架 → 同可用区 → 更大范围
```

具体等级依赖集群提供的拓扑信息，这里只表达处理方向。

降级只放松通信偏好。Pod 原有硬约束和资源要求仍必须满足，每个 Pod 的最终节点也仍须来自它通过 Filter 的候选列表。

本版不为维持通信偏好而无限等待。放宽通信范围以后仍然没有可行放置，才交回调度失败结果，进入已有的错误处理流程。

### 规则二：冲突时，按通信关系的妥协顺序降级

多条关系争用有限的放置空间时，优先保护不应妥协的关系，让可以先妥协的关系扩大范围。

例如，两条关系的放置权重相同，但其中一条更允许降级，就先放松这条。放置权重参与方案评价，妥协顺序决定发生冲突时先放松谁，两者分别保留。

降级以后，只要最终放置可行，就属于正常调度结果。不能因为关系没有达到期望等级，就把已成功放置的任务送入 Fail 或 Retry。

我们保留期望等级和实际等级，便于以后判断有没有改善机会。运行后如何重新优化、拓扑变化如何触发尝试、Agent 如何介入，都属于后续工作，本版不建立持续迁移机制。

## 5. 通信域与集中偏好怎样参与

这里的通信域指：**为这个 Group 选择的一组承载 Node，以及这些 Node 所处的拓扑范围。** 它可以是同节点，也可以跨多个节点、机架。

选择时一起考虑：

1. 重要通信关系能否得到期望的靠近程度。
2. 域内资源能否容纳计划放进去的所有成员。
3. 多套方案都可行时，哪一套更符合集中偏好、放置后还有更合适的余量。

用户提出的核心意图是：资源宽裕时，主动找能同时承载多条关系的范围，减少先满足一条、再让另一条发生冲突的情况。

例如 A—B、A—C 都希望同节点，node1 能容纳 A、B、C，而 node2 只能容纳其中两个。对于偏好集中的组，node1 可以同时满足两条关系，应当得到更好的评价。

域选择要考虑整个 Group。Partial 后续只重排部分成员时，也要结合同组当前的位置，尽量保持一致的放置方向；不要求把冻结 Unit 强制合并。

通信域在规划中可以先圈定，也可以随着方案组合逐步形成。具体搜索方式尚未决定。

选择一个有余量的域，不代表已经预留或独占了这个域。真正的资源预留仍由后续 Assume 机制处理。域选择用于减少冲突，不能保证以后没有竞争。

## 6. 处理流程

```text
Pod Filter + Pod Score
        ↓
第一步：为每条通信关系生成候选放置
        ↓
第二步：reduce，组合出组方案并校验资源
        ↓
第三步：评价通信效果，保留少量不同方案
        ↓
其他组语义继续评价这些方案
        ↓
汇总评价，选出最终 Pod → Node 计划
        ↓
Assume → Bind
```

### 第一步：链路候选

对 A—B 这条关系，读取 A、B 各自的 NodeList：

- 同节点候选：A、B 都能放置的某个节点，记录为 `(A=node1, B=node1)`。
- 跨节点候选：满足指定拓扑关系的一对节点，记录为 `(A=node1, B=node2)`。
- 每项候选保留端点的位置、达到的靠近等级和相关 Pod 基础分。

这里检查链路涉及的成员是否放得下；不同链路合并后的资源检查继续在 reduce 中完成。

优先使用期望等级。冲突需要降级时，再放宽候选范围。不能先永久删掉所有较远候选，导致后面无从降级。

不参与通信声明的本轮成员，也要根据自身候选节点进入最终组方案，不能在这一步遗漏。

### 第二步：reduce 组合与资源检查

将多条关系的候选合并成覆盖本轮成员的放置方案。

组合时检查四件事：

1. **共享成员位置一致。** A—B 与 A—C 中的 A 必须落在同一个节点。
2. **资源按成员计算。** A 被两条关系引用，CPU、内存等需求只计算一次。
3. **整套方案放得下。** 两条关系各自可行，不代表它们合起来也可行；要在节点资源副本上累计试放本轮成员。
4. **已有位置参与约束。** 同组当前已绑定成员的位置作为参照，不能在方案里随意改写。

遇到无法共同满足的通信要求，按照规则二降级，再继续组合。具体如何换候选、回退和展开搜索，以后再选算法，本次不展开。

例如节点只能容纳两个成员时，A—B、A—C 都要求同节点，两条关系就无法一起满足。若 A—C 允许先妥协，可以保留 A、B 同节点，让 C 放到更远的位置。

### 第三步：评价与保留

只对可行方案评价通信效果。评价至少能解释：

- 哪些关系达到了期望等级。
- 哪些关系降级了，实际到了哪个等级。
- 重要关系的满足情况。
- 方案的集中程度，以及放置后的资源余量情况。

**每套方案要给出可供最终汇总的通信分数，同时保留分项结果。** 分数范围、归一化方式、与其他语义及 Pod 基础分的合并权重，留到统一汇总环节一起确定；本文没有预设已经敲定的公式。

保留方案时，要留下不同的放置方式。例如集中在一个节点的方案、跨两个节点的方案，都可能交给后续语义比较。我们还没有决定具体的去重和多样性算法。

通信评价不会直接选定唯一计划。后续语义可以对同一批方案评分；如果它有明确的硬约束，也可以淘汰不满足的方案。

## 7. 备选数量与异步搜索，先做到哪里

目前的决定是：**先产生少量可行备选，继续往下走，不为穷尽所有方案堵住流程。** 讨论中的“三四套”说明预期规模，不是已经确定的配置值。

后续可以探索：前台拿到足够方案就交给后面的评分，后台继续寻找其他方案；需要时补充使用，最终选定计划后停止后台搜索。

本版只记录这个方向，不引入后台搜索线程。搜索多少套、时间预算、何时接受新增方案、停止信号和资源快照有效性，等优化算法时一起处理。

不管将来用哪种算法，第一版框架要保留三个能力：传递多套方案、保留不同放置方式、携带每套方案的评分与解释。

## 8. 对应到现在的源码

输入入口是 [scheduler/score.go](../src/scheduler/score.go) 的 `GroupScoreInput`。完整 Pod、NodeInfo、冻结的 Placement 声明和跨 Unit 上下文已放入当前输入，以下按字段说明用途。

| 字段 | 本层如何使用 |
| --- | --- |
| Pods | 本轮成员及其资源需求、约束 |
| PodScores | 每个 Pod 通过 Filter 后的节点候选和基础分 |
| NodeInfos | 本轮资源与拓扑视图，供试放使用 |
| Mode | 保留本轮的提交模式，不在通信层改写 Unit 成员 |
| Placement | 冻结组声明中的通信关系、权重、优先级及资源整合开关 |
| BoundPeers | 同组当前已绑定成员的位置参照 |
| Context | 同组其他 Unit 的进度、计划及历史记录 |

BoundPeers 已在 NodeInfo 的已有 Pod 占用中，不能为了计算组关系再次扣减资源。成功历史用于了解过去的位置，不等于成员现在仍在那里；其他 Unit 的计划也不能直接当成已绑定事实。相关实现见[组上下文与成功记录](group-context.md)。

当前 `PlanGroup` 对外仍返回最终 `map[PodRef]string`。未来的候选生成、通信评价和其他语义评价，放在该步骤内部组织；最终选出的方案再转换成这个计划交回 Executor。

本地已增加 CandidatePlan、插件实现目录、CR 配置透传和本轮通信放置主线，没有后台搜索线程。跨 Unit 端点、集中评分和最终汇总仍待实现。

## 9. 本轮确定与后续再定

已经确定：

- 以 Group 的通信关系指导本轮放置，跨 Unit 考虑当前同组成员。
- 先生成链路候选，再 reduce 成组方案。
- 冲突时允许降级，按通信关系的妥协顺序处理。
- 组合时累计检查资源，共享 Pod 只计一次。
- 通信域、集中偏好和资源余量参与方案选择。
- 产出多套不同放置方案，携带通信分数和降级明细。
- 后面的语义继续评价同一批方案，最后统一选定计划。

后续再定：

- 组声明的快照透传、成员端点解析和拓扑等级到节点标签的映射。
- reduce 的具体搜索算法、候选数量和时间预算。
- 评分公式、不同语义之间的分数合并方式。
- 后台搜索、运行后重新优化及 Agent 介入方式。

后续讨论已确定第二项为可选的资源整合评价，不增加独立的同步或故障优化语义。两项如何衔接、明天从哪里开始，见[第一版组评分方案](group-scoring-design.md)。
